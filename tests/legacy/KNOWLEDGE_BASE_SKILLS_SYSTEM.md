# 技能系统 (Skills System) 开发故障与集成测试回顾

## 1. 现象描述
在开发过程中，Skills 系统经历了多次“代码逻辑看起来正确，但集成测试/实际运行失效”的情况。具体表现为：
- 控制台显示技能已激活，但后端收到的是空列表。
- 集成测试在 Mock 环境通过，但在真实浏览器环境失败。
- 修复了变量崩溃，但刷新后再次出现。

## 2. 根因分析 (Root Cause Analysis)

### A. 物理层：幽灵函数 (Ghost Code)
**问题**：`useChatStore.ts` 超过 4000 行，且在多次自动化重构中产生了多份 `patchedSendMessage` 副本。
**后果**：开发者一直在修复 2300 行之后的代码，但 JS 引擎优先执行了位于 190 行处的陈旧副本。
**教训**：在大文件上进行 `replace` 或 `sed` 操作前，**必须**先执行全文件唯一性检查。

### B. 协议层：Tauri 2.0 命名协议陷阱
**问题**：Rust 端定义为 `active_skill_ids`。
**逻辑错误**：前端也发送了 `active_skill_ids`。
**真实行为**：Tauri 默认将 Rust 蛇形命名参数映射为前端驼峰。前端必须发送 `activeSkillIds` 才能被后端成功反序列化。
**后果**：数据在跨语言调用时发生“静默丢失”，后端始终收到 `None`。

### C. 运行时：Zustand 实例隔离
**问题**：Vite 这种 ESM 编译器在热更新 (HMR) 或代码拆分 (Chunking) 时，可能导致 `import` 进来的 Store 实例与 `window` 挂载的实例不是同一个物理对象。
**后果**：UI 开关操作的是实例 A，`sendMessage` 引用的是实例 B。
**解决方案**：采用 **绝对全局单例模式**，强制将关键状态同步到 `window.__IFAI_ACTIVE_SKILLS__`。

### D. 模型层：近因效应与指令冲突
**问题**：RAG 注入的项目上下文（如“请使用中文回答”）位于 System Prompt 后部，覆盖了位于前部的技能指令。
**后果**：LLM 产生纠结并开始“自我解释”，而非直接执行。
**解决方案**：**双重注入 + 置底策略**。利用 LLM 的 Recency Bias（近因效应），在 System Prompt 的绝对末尾再次强制注入技能指令。

## 3. 防御性编程准则 (Actionable Guidelines)

1. **唯一性审计**：修改核心函数前，先运行 `grep -c`。如果计数 > 1，严禁进行局部替换，必须先执行物理去重。
2. **协议先行**：Tauri `invoke` 的参数命名必须优先对齐驼峰（CamelCase），且在后端打印 `active_skills: {:?}` 进行显式验证。
3. **全局锚点**：跨模块、跨环境（E2E）的状态同步，不要仅依赖模块单例，必须提供物理挂载点（如 `window.__DEBUG__`）进行状态强行对齐。
4. **E2E 高保真原则**：
   - 避免过度 Mock `invoke`。
   - 必须包含“内容级断言”（例如：断言页面出现了日文字符）。
   - 在测试开始前，显式清理 Joyride 等遮罩层 UI。

## 4. 绿灯基准 (Green Phase Baseline)
目前保留的 `tests/e2e/skills_flow_stable.spec.ts` 已实现：
- 真实 UI 交互模拟。
- 逻辑层状态强制同步验证。
- 后端报文拦截与驼峰协议断言。
- 模拟后端日文返回的内容级闭环断言。
